# github-ready

## 概述

把一个功能已经做完的 skill 项目整理到可以公开发布到 GitHub 的状态。核心原则：先检查并出一份报告，只问用户一次，确认后一次改完，改完由一位不知道修改经过的审核专家评审改前改后的优劣。

下面七条同时成立，就算可以发布：

1. 文件夹布局是一键安装器（`npx skills add`）认得的，推荐 `skills/<name>/SKILL.md`。
2. 仓库根有中文 `README.md` 和英文 `README.en.md`，各含 README 标准规定的八节，章节一一对应。
3. README 里写全 Claude Code、Codex CLI、OpenCode 三个工具的安装说明，安装路径正确。
4. 仓库根有 LICENSE，类型与 README 写的一致。
5. README 的「用起来长什么样」一节有一段取自真实使用的演示。
6. `SKILL.md` 的简介（头部的 `name` 和 `description`）符合 superpowers 规范：`description` 只写什么时候用，不概括流程，用第三人称；README 触发表里的每条说法在 `description` 里都找得到。
7. `SKILL.md` 的正文符合 superpowers 规范：引用的附带文件都在，没有本机路径，没有只在某一个工具上才成立的内容。

检查分两类，下文一直用这两个说法：

- **脚本能检查的**：答案确定，由 `scripts/checkup.py` 查，每次结果相同。比如某一节在不在、路径写没写错、LICENSE 有没有。
- **需要人判断的**：脚本判不了，由你读原文判断。比如一句话有没有说清楚、演示像不像真的。

## 何时使用

适用：

- 用户要把一个 skill 项目发布到 GitHub，或想知道还缺什么。
- 用户要复查一个已经发布的 skill。

不适用：

- 项目里没有 `SKILL.md`。脚本会停下并说明原因。
- 用户要推送、创建仓库，或要修改 skill 的功能代码。这些事本 skill 不做。
- 用户要确认 skill 在某个工具上能否运行。本 skill 不替用户安装或试用 skill，为取演示记录而使用一次除外。

## 附带文件

路径都相对本文件所在的文件夹。

| 文件 | 内容 | 什么时候用 |
|---|---|---|
| `scripts/checkup.py` | 体检脚本，只读，不改被检查的项目 | 第 1 步和第 5 步运行 |
| `references/readme-standard.md` | README 八节各自的要求、三个工具的路径表、文件夹布局和可移植性的规定 | 第 2 步通读；第 4 步起草哪一节就再看哪一节 |
| `references/superpowers-standard.md` | `SKILL.md` 的写法：简介和正文 | 第 2 步通读；第 4 步改 `SKILL.md` 时再看 |
| `references/reviewer.md` | 审核专家的工作说明：评审时看什么、怎么判定、结果怎么写 | 第 6 步读 |
| `rules/*.yaml` | 脚本用的数据 | 脚本自己读，不必打开 |

## 流程

1. **体检**：运行 `python scripts/checkup.py <项目路径> --json <结果文件>`，按「速查」里的退出码决定继续还是停止。
   - 用户没给路径就用当前目录。
   - 结果文件放在系统的临时目录。放进被检查的项目会给用户留下多余的文件。
   - `python` 不存在就用 `python3`，需要 3.9 或更新的版本。
2. **复查**：读项目的两份 README 和 `SKILL.md`，对照两份标准做两件事。
   - 结果里状态为 `suspect` 的条目，逐条定为「是问题」或「不是问题」。
   - 两份标准各节里「需要人判断的」项，逐条判断。

   脚本已判为 `pass` 或 `fail` 的不重复判断。每个问题按「速查」里的规则归为必须修或建议。
3. **报告，等用户确认**：按「报告格式」写。检查对象确定之后，全程只在这里问一次，所以打算做的每件事、需要用户回答的每件事都要写进这份报告。
   - 用户不同意就结束，不改任何文件。
   - 既没有必须修的问题、也没有建议时，给出报告就结束，不用等确认。
4. **补齐**：按「补齐的做法」改，中途不再提问。
   - 结果里 `git` 一项不是 `clean` 时，动手之前把报告「我打算动的文件」里要修改、移动的文件各复制一份到系统的临时目录。第 6 步要拿它们和改后的文件比较。
   - 建议项默认不改。用户确认时点名要改的那几条，在这一步一并改。
   - 用户确认了但没有给齐的资料，对应的那几项不做，收尾时列为未解决。
5. **再体检，并重读改过的地方**。
   - 重跑第 1 步的命令。
   - 把这次改过、新写的每一处，按第 2 步的标准重读一遍。脚本只查得出一部分问题；新写的句子是否清楚、是否写进了这次检查和修改的经过、中英两份是否还对得上，只有重读才能发现。
   - 还有能修的问题就回到第 4 步。重跑后没有新出现的必须修、重读也没有发现新问题时，进入第 6 步。
6. **评审**：读 `references/reviewer.md`，让审核专家比较改前和改后。刚改完的人容易认为自己的改动都是对的，所以这一步交给不知道修改经过的审核专家。用户在第 3 步说了不要评审的，或者第 4 步没有改任何文件的，跳过这一步。
   - 准备四样材料：改前改后的差异；第 3 步的报告和用户的答复；第 1 步的结果文件和第 5 步最后一次的结果文件；两份标准。差异的取法：`git` 一项是 `clean` 的，在项目里运行 `git diff HEAD`，新建而没有被 git 跟踪的文件另外列出全文；其他情况，拿第 4 步留的副本和改后的文件对比。
   - 能派出一个不带本次对话内容的独立子任务时，把 `references/reviewer.md` 和四样材料交给它（贴全文或给文件位置都可以），并告诉它改后的项目在哪里、只能读不能改，不附加自己对改动的解释。不能派时，自己按该文件逐条评审，并在评审结果里写明「本次不是独立评审」。
   - 评审结果里的事实错误，在用户同意的修改范围之内、又能由本 skill 改的，改正后重跑第 1 步的命令，并重读改正的地方。评审指出超出用户同意范围的改动，撤回。这样的改正只做一轮，不再送评审，否则可能没完没了地循环。
   - 判断类意见和其余判为「倒退」的改动不动，连同撤回办法交给用户决定。
   - 评审结束后按「结束时交代什么」收尾。

## 速查

**退出码**

| 退出码 | 含义 | 怎么办 |
|---|---|---|
| 0 | 体检完成 | 继续第 2 步 |
| 2 | 不是 skill 项目 | 把脚本打印的原因告诉用户，停止 |
| 3 | 找到多个 `SKILL.md` | 把候选列给用户选，加 `--pick <相对路径>` 重跑，在报告开头写明选的是哪个。这一问是为了确定检查对象，不算在「只问一次」之内 |
| 4 | `SKILL.md` 头部无法解析 | 把脚本打印的原因告诉用户，停止 |
| 5 | 本机没有 git | 告诉用户需要先安装 git，停止 |
| 其他 | 脚本出错 | 把脚本的输出原样告诉用户，停止 |

**结果文件**（JSON）的顶层项

| 项 | 含义 |
|---|---|
| `name` | skill 的名字，报告标题用它 |
| `skill_md` | 被检查的 `SKILL.md` 的相对路径 |
| `git` | `clean`：用 git 管理且没有未存档的改动。`dirty`：有未存档的改动。`no-repo`：项目文件夹本身不是一个 git 仓库的顶层，要么没有用 git，要么只是某个大仓库里的子文件夹 |
| `summary` | 三种状态各有多少条 |
| `findings` | 逐条结果，每条含 `rule`（规则名）、`status`、`file`、`line`、`detail`（说明） |

**`status` 的取值**

| 取值 | 含义 | 怎么办 |
|---|---|---|
| `pass` | 达标 | 不用管 |
| `fail` | 必须修的问题 | 写进报告。能由本 skill 改的第 4 步修；要用户决定的在报告里问 |
| `suspect` | 脚本拿不准 | 第 2 步定性 |

**规则名的开头**

| 开头 | 查的是什么 |
|---|---|
| `STRUCT-` | 文件夹布局、头部和 LICENSE |
| `NAME-`、`DESC-` | 简介 |
| `BODY-`、`REF-`、`PORT-` | `SKILL.md` 的正文和附带文件 |
| `README-ZH-EXISTS`、`README-EN-EXISTS` | 两份 README 在不在 |
| `S1` 到 `S8` | README 的第几节。名字末尾的 `:README.md` 或 `:README.en.md` 表示是哪一份 |
| `S45-PATHS` | 第 4、5 两节合起来查的安装路径 |
| `S45-ODDPATH` | 某个工具的小节里，除了对的路径之外有没有另写一条不在路径表里的路径 |
| `REPO-CONSISTENT` | 安装命令里的仓库地址前后是否一致 |

脚本给的行号是 1 的条目，行号多半是占位的。「缺某个文件」这一类在报告里只写文件名；其他的到原文里找到真实行号再写进报告。

**问题归哪一级**。归到哪一级决定了改不改用户的文件，所以按规则归：

| 级别 | 包括 |
|---|---|
| 必须修 | 脚本判为 `fail` 的；`suspect` 复查后定为「是问题」的；违反了标准里明文「内容要求」的（该有的没有、写错了、写了开发过程）；写的内容与事实不符的（数字前后对不上、文件树与实际产物不符、演示的样子与这个 skill 现在的输出不符） |
| 建议 | 内容要求都满足，只是可以写得更好的；数量类的要求没有达到的（要求 2–4 句只写了 1 句、要求 2–4 条只列了 1 条）；标准里明说「提一句建议」的 |

## 报告格式

```markdown
# 体检报告：<skill 名字>

检查对象：<SKILL.md 的相对路径>
脚本检查：<N> 项通过，<N> 项必须修，<N> 项拿不准
人工复查：<N> 项必须修，<N> 项建议

## 必须修的问题
1. <一句话说问题>
   位置：<文件>:<行号>
   原因：<为什么是问题，对读者或安装的人有什么后果>
   打算怎么改：<具体改法>

## 建议（默认不改）
1. <问题>（<文件>:<行号>）：<理由>。改法：<具体改法>

## 我打算动的文件
- 修改：<文件>
- 新建：<文件>
- 移动或改名：<原位置> → <新位置>
- 改 description（会影响这个 skill 何时被调用）：<原文> → <新文>

## 改完能不能撤销
<按 git 状态写一句>

## 需要你回答的
1. 按上面的方案修改吗？
2. 建议里要一并改的是哪几条？不说就都不改。
3. 改完后会请审核专家评审一次改前改后的优劣，结果一并交给你。不需要评审请说明。
4. <项目里查不到、需要你提供的资料，或需要你做的决定，一样一条>
```

- 五个小节都保留，没有内容的写「无」。用户靠固定的位置找信息。
- 每条结论给出文件、行号、理由。没有这三样，用户无从核对。
- 复查后定为「不是问题」的不写进报告。
- 计数：同一处原文算一项，脚本对它报了几条都算一项；中英两份 README 里的同一个问题算一项。
- 必须修但不该由本 skill 动手的问题（比如 skill 正文该写什么、项目里互相矛盾而查不出哪个对的事实），照样列在「必须修的问题」里，「打算怎么改」写「不改，需要你来定」并说明原因，同时在「需要你回答的」里列出。
- 「改完能不能撤销」按 git 状态写：`clean` 可以用 git 查看和撤销；`dirty` 这次的修改会和已有的未存档改动混在一起；`no-repo` 分两种，项目在某个大仓库里的，改动可以在上级仓库里查看和撤销，完全没有用 git 的，改完不能撤销。
- 「需要你回答的」第 4 条起列两种事：项目里查不到的资料，常见的是仓库地址（`owner/repo`）、LICENSE 的类型和版权人、一次真实使用这个 skill 的记录（用户提供，或同意当场用它一次取得）；需要用户做的决定，比如缺的附带文件是补上还是删掉引用。每条写明不回答会怎样。查得到的不问。

## 补齐的做法

总的规矩：只改不达标的地方。用户手写的句子带着他自己的判断，整篇重写多半更差，所以已有的内容只动出问题的那一处。新写进去的内容同样受两份标准约束，尤其不能把这次检查和修改的经过写进 README，也不写防御性表述（定义见 README 标准的「全局规定」）。

| 问题 | 做法 |
|---|---|
| 文件夹布局安装器认不出 | 移到 `skills/<name>/`。项目用 git 管理时用 `git mv`，保留文件历史。移完后把 README 里引用旧位置的地方一起改掉 |
| 缺 README 或缺某一节 | 按 README 标准里那一节的「内容要求」起草，素材取自 `SKILL.md` 和项目里的文件。项目里查不到的事实不编，留给用户提供 |
| 中英两份不对应 | 中文是 `README.md`，英文是 `README.en.md`。两份里同一处的事实（路径、命令、步骤）要相同：一份必须改时，另一份对应的位置改成同样的内容，即使它原来的写法本身不算错。只是某一份的措辞有问题，只改那一份 |
| 安装路径不对 | 改成 README 标准第 4 节路径表里的路径，手动安装和一键安装装到同一个地方 |
| 简介不符合规范 | 按 superpowers 规范的模板改写 `description`，原有的触发说法全部保留，否则 README 触发表会对不上。`name` 不符合格式的只写进报告：改名会连带改文件夹名和所有安装命令，由用户决定 |
| 触发说法对不上 | 默认改 README 的触发表去迁就 `description`。只有表里的说法明显是用户想要的触发词时，才往 `description` 里加 |
| 正文引用的附带文件不存在 | 文件改了名或挪了位置的，把引用改对。文件确实没有的，写进报告由用户决定补文件还是删引用；用户确认时没有回答的，不动，收尾时列为未解决 |
| 正文有本机路径，或只属于某一个工具的内容 | 第 2 步定为「是问题」的，改写那一句，不动别处。脚本结果的 `detail` 里有改法建议的照它改 |
| LICENSE 缺失或对不上 | 按用户确认时给的类型和版权人生成，README 第 8 节写成同一个类型 |

凡是改 `description`，都在报告的「我打算动的文件」里写明原文和新文。

**演示**（README 的「用起来长什么样」一节）单独规定：

- 演示指代码块里的那段记录。它是一次真实使用这个 skill 的记录，可以删减，不能编造。记录里的本机路径换成示例路径。
- 演示写成对话的形式，每段话前面标明「用户：」或「AI：」，让没用过命令行的人一眼看懂。只有一种改写是允许的：用户输入的是斜杠命令或带本机路径时，改写成意思相同、用到一条触发说法的自然的话。AI 的回复只能删减，规则编号一类新手看不懂的行删掉。
- 代码块前后的说明句（阅读约定、演示后的总结）不属于记录，可以按标准改写，但不能写得和记录对不上。
- 这次体检本身不能当演示。体检的内容是「这份 README 哪里不对、怎么改」，写进去就成了开发经过。
- 记录有两个来源：用户提供；或用户同意后，按被检查 skill 自己的 `SKILL.md` 真实用它一次，记下输入和输出，运行产生的文件不留在项目里。它需要的输入用户没给，或它中途必须有人回答的，就不运行。
- 已有的演示有问题时，只改出问题的那几行，而且除了上面允许的那一种改写之外只能删减：删掉对不上的那一条可以，改一个数字让它对上属于编造。靠删减解决不了的问题留着，收尾时说明要等新的真实记录。整段替换只在拿到新的真实记录时才做。
- 英文 README 里的演示，原始输出不是英文的就放译文，并在演示前说明是译文。
- 没拿到记录就不写、不换演示，收尾时说明这一项留给用户。

## 结束时交代什么

- 改前和改后的对比，分两行：脚本检查的通过和必须修各多少条；人工复查的必须修和建议各多少条、这次改掉了几条。
- 实际改动、新建、移动了哪些文件。
- 评审结果的全文，按 `references/reviewer.md` 的输出格式。之后写明：评审指出的事实错误里改正了哪几条、撤回了哪几处；哪些「倒退」和判断类意见没有动，等用户决定。跳过评审的，写明没有评审和原因。
- 还没解决、留给用户的事，以及原因。
- 能用 git 查看改动的，提醒可以用 `git diff` 逐行查看。
