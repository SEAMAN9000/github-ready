# 审核专家：评审这次修改

这份文件是 github-ready 流程里「评审」一步的工作说明，在补齐完成、再体检并重读之后读。读它的是负责评审的那一位：执行者能派出不带上下文的独立子任务时，由子任务读；不能派时，由执行者自己读并逐条照做，并在结果里写明「本次不是独立评审」。评审要做的事：比较目标 skill 项目改前和改后的状态，把每一处改动判定为改进、无差别或倒退。

## 拿到的材料

1. 改前改后的文件差异（`git diff` 的输出，或改前副本与改后文件的对比）。
2. 第 3 步给用户的报告和用户的答复。两者合起来就是用户同意的修改范围。
3. 改前、改后两次脚本体检的结果。
4. `references/readme-standard.md` 和 `references/superpowers-standard.md`，下文合称「两份标准」。

- 判定只以这四样为准。材料里夹带了执行者对改动的解释时不采用：解释会让评审沿着执行者的思路判断，查不出执行者自己没有发现的问题。
- 差异里看不全、要读上下文才能判断的地方，能读到改后的文件就读，读不到就列入「没能验证的」。
- 缺某一样材料时照常评审，把因此判不了的条目列入「没能验证的」。

## 怎样算一处改动

报告里的一条问题对应的修改算一处；中英两份 README 对应位置的同一个修改算一处，两份改成了不同的内容时拆成两处分别判定；移动或新建一个文件算一处。差异里对不上报告任何一条的修改，每个位置单独算一处。这样计数与报告一致，用户可以拿报告逐条对照。

## 三种判定

| 判定 | 条件 |
|---|---|
| 改进 | 能指出改前违反了两份标准的哪一条，或与哪个文件的事实不符，改后符合 |
| 无差别 | 只换了说法、排版或顺序；或者找不到改进的依据 |
| 倒退 | 把原本正确的内容改错；改后违反两份标准；超出用户同意的范围；演示被改写；写进了这次检查和修改的经过 |

- 每条判定都写依据：指到文件和行号，或指到两份标准里的哪一节哪一条。没有依据的判定用户无从核对。
- 改动的数量、篇幅的增减、排版是否更整齐，都不能当作依据。找不到依据的「改进」一律判「无差别」。
- 含有事实错误的一处不能判为改进。改前就错、改后仍然错的，判「无差别」，同时列入「事实错误」。
- 行号用改后文件的行号；被删掉的内容用改前的行号，并注明「改前」。

## 依次从三个角度看

每一处改动都按下面的顺序看三遍。三个角度查的东西不同，合在一起看容易漏掉其中一类。

### 一、事实

对照 `references/readme-standard.md` 第 4 节的路径表、第 5 节和末尾的「文件夹布局」一段，查改后的内容：

- Claude Code、Codex CLI、OpenCode 三个工具的安装路径是否都在路径表之内，有没有漏掉某个工具，有没有把仓库里的 `skills/<name>/` 写成安装路径。
- 同一个工具的手动安装和一键安装是否装到同一个地方；安装命令里的仓库地址是否前后一致。
- 斜杠加名字的调用方式是否只出现在 Claude Code 小节；Codex CLI 一节是否写明文件名保持 `SKILL.md`。
- 文件夹移动之后，README 和 `SKILL.md` 里引用旧位置的地方是否都改了；`SKILL.md` 正文引用的附带文件是否都存在。
- README 写的许可证类型与 LICENSE 文件是否一致。
- 强制的内容有没有被写弱，例如「必须」改成了「可选」「视情况」。

对错只按两份标准和项目里的文件判，不按记忆判：三个工具的约定会变，记忆里的路径可能已经过时。认为标准本身写得不对时，写进「范围外的观察」，判定仍按标准。

### 二、读者

读者是没有技术背景、第一次看到这个仓库的人。查中英两份 README 和 `SKILL.md` 简介里改过的地方：

- 改后的句子能否一遍读懂，读完是否知道下一步做什么。篇幅长短本身不算优劣。
- 中英两份同一处的事实（路径、命令、步骤、数字）是否相同，章节是否仍然一一对应，有没有一份改了而另一份没改。
- `description` 有改动时：原有的触发说法是否全部保留，README 触发表里的每条说法是否仍然找得到，是否只写什么时候用，有没有出现「我」「你」。
- 新写的内容有没有本机路径，有没有只在某一个工具上才成立的说法，有没有防御性表述（定义见 `references/readme-standard.md` 的「全局规定」）。

### 三、证据

- **范围**：每一处改动对得上报告里的哪一条。报告里列为建议的，只有用户在答复里点名的才能改。对不上任何一条的改动判「倒退」，因为用户只同意了报告里写出的那些事。
- **演示**：演示指 README「用起来长什么样」一节代码块里的记录，只允许三种改动：删减；把本机路径换成示例路径；把用户输入的斜杠命令或带本机路径的话改写成意思相同的一句自然的话，并给每段话标明「用户：」「AI：」。AI 的回复里新增的行、改过的数字或输出，算作编造，除非用户的答复里提供了新的真实记录。演示的内容是这次体检和修改本身的，判「倒退」。代码块前后的说明句可以改写，但要查它与记录是否对得上。
- **改坏**：被改动的原文是否本来就符合标准。本来正确而被改动的，查改后是否仍然正确。
- **脚本通过但没有达标**：两次体检结果里从 `fail` 或 `suspect` 变成 `pass` 的每一条，都读改后的原文确认内容确实达标。常见情形：标题对上了，节里却没有标准要求的内容；加了一个脚本认得的词，句子的意思没有变；用了脚本认不出的写法，例如换一种说法概括流程、换一种格式写本机路径。从 `pass` 变成 `fail` 或 `suspect` 的条目，找到对应的改动，判「倒退」。两次都是 `pass` 也不能当作达标的证明：脚本只认得一部分写法，判定以读到的原文为准，脚本漏查的情况写进「范围外的观察」。

## 事实错误和判断类意见

每条发现归入两类之一。评审之后，事实错误会被直接改正，判断类意见只报告给用户、不动文件。归错了类，确定的错误会被当成意见搁置，意见会被当成错误直接改掉。

- **事实错误**：摆出原文，再摆出标准的条文或项目里的文件，就能证明，不需要读者相信评审的眼光。例如路径不在路径表内、引用的文件不存在、中英两份的命令不同、演示代码块里出现了改前没有的行、改动不在用户同意的范围内。
- **判断类意见**：句子是否清楚、取舍是否合适、例子是否贴切。

拿不准属于哪一类时归为判断类意见，并在依据里写明还缺什么证明。

表格的「依据类型」一栏：这一处有事实错误就填「事实」，否则按依据的性质填。总结里的「事实错误 N 处」数的是「事实错误」清单的条数。一处改动可以同时出现在「事实错误」和「建议撤回」两个清单里，例如超出范围的改动。

## 不做的事

- 不修改任何文件，不推送。评审只出结果，改不改由后续流程决定。
- 不向用户提问。整个流程只在报告那一步问用户一次。
- 不评价 github-ready 自身的流程设计，也不评价目标 skill 的功能设计。
- 不提出修改范围之外的新要求。看到范围之外的问题，写进「范围外的观察」，不计入判定和计数。
- 不给出改写稿，只指出问题在哪、依据是什么。
- 不引用没有读到的原文，不把没有执行过的命令写成「可以运行」。

## 输出格式

照下面的模板写，小节都保留，没有内容的写「无」。用户靠固定的位置找信息，所以不增减小节，不调换顺序。每句话让没有技术背景的人一遍读懂。

```markdown
# 评审结果：<skill 名字>

评审方式：<独立评审 / 本次不是独立评审>
总结：改进 <N> 处，无差别 <N> 处，倒退 <N> 处；事实错误 <N> 处。

## 逐处判定
| 编号 | 改了什么 | 位置 | 判定 | 依据 | 依据类型 |
|---|---|---|---|---|---|
| 1 | <一句话> | <文件>:<行号> | <改进 / 无差别 / 倒退> | <标准的哪一节哪一条，或哪个文件的哪一行> | <事实 / 判断> |

## 事实错误
1. <哪里错了>（<文件>:<行号>，对应第 <编号> 处）。证明：<对照的标准条文或文件>。后果：<读者或安装的人会碰到什么>

## 建议撤回
1. 第 <编号> 处：<原因>。撤回办法：<具体做法>

## 没能验证的
1. <什么事>：<为什么验证不了>。<怎样可以验证>

## 范围外的观察（不计入判定）
1. <观察>（<文件>:<行号>）
```

- 「建议撤回」列出所有判为倒退的改动。撤回办法写到用户可以照做：整个文件撤回的，写用 git 把哪个文件恢复到改前的状态，并给出命令；只撤回一段的，写明文件、行号范围，以及差异里以 `-` 开头的哪几行原文要放回去；文件被移动的，写明移回哪里。`git` 一项看改前那一次的体检结果，改后那一次必然是 `dirty`。改前是 `no-repo` 且项目完全没有用 git 的，写明只能照差异手工改回。
- 「没能验证的」至少交代这几件事做了没有：有没有在 Claude Code、Codex CLI、OpenCode 上真实安装过；安装命令有没有执行过；演示的原始记录有没有看到；触发说法有没有试过。没有做的照实写，不省略。

## 返回前核对

- 总结里的四个数与表格、清单的条数一致。
- 差异里的每一处修改都在表格里有一行，每一行都有位置和依据。
- 每条事实错误都附了证明；证明不了的已经移到判断类意见。
- 每条判为倒退的改动都在「建议撤回」里有一条可以照做的办法。
- 全文没有改写稿，没有范围之外的要求混进判定。
