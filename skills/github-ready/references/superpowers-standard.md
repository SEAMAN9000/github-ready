# superpowers 规范：SKILL.md 的写法

本规范规定一个 skill 的 `SKILL.md` 怎么写，取自 [superpowers](https://github.com/obra/superpowers) 项目的 skill 撰写约定。

一个 skill 分三层，AI 读到它们的时机不同：

| 层 | 位置 | AI 什么时候读 |
|---|---|---|
| 简介 | `SKILL.md` 最开头两行 `---` 之间的 `name` 和 `description` | 始终看得到 |
| 正文 | `SKILL.md` 里第二行 `---` 之后的全部内容 | 根据简介判断要用这个 skill 之后 |
| 附带文件 | skill 文件夹里的其他文件 | 正文指到它时 |

本规范分两部分：简介，正文（含正文怎么引用附带文件）。每项要求分两类检查：「脚本能检查的」由 `scripts/checkup.py` 判定，「需要人判断的」由读原文判断。

## 第一部分 · 简介

简介只回答一个问题：现在该不该读这个 skill。

### name

- 内容要求：
  - 只用小写英文字母、数字和连字符（`-`），不超过 64 个字符。
  - 名字说出这个 skill 做的事，动词在前更好：`creating-reports` 好于 `report-helper`。
- 脚本能检查的：格式和长度。
- 需要人判断的：只看名字能否猜到用途。

### description

- 内容要求：
  1. **只写什么时候用。** 中文用「……时使用」的句式，英文用 "Use when …" 开头。写具体的情形：用户在做什么、遇到了什么、想得到什么。
  2. **不写流程和做法。** 不概括步骤，不写「先……然后……」，不写内部怎么实现。理由：简介里一旦概括了流程，AI 可能照着简介做，不去读正文，正文里的细节就失效了。
  3. **写出用户会说的话。** 在使用情形之后可以加「触发说法：」，列出用户的原话和斜杠命令，中文英文都列。README 触发表里的每条说法都要在这里找得到。
  4. **用第三人称。** 不出现「我」「你」。简介会被放进 AI 的系统提示里，人称不一致会干扰识别。
  5. **容易用错的地方写一句不适用的情形。** 例如只处理哪一类项目、会不会修改文件。
  6. **长度不超过 1024 个字符**，这是规范的上限；建议控制在 500 个字符以内。超过 500 时，通常是把正文的内容写进了简介。
- 脚本能检查的：
  - 不超过 1024 个字符，超过是必须修的问题。
  - 超过 500 个字符，标为 `suspect`。
  - 找不到「……时使用」或 "Use when" 这类句式，标为 `suspect`。
  - 出现第一人称或第二人称的词，标为 `suspect`。
  - 出现「然后」「首先」「确认后」这类表示步骤的词，标为 `suspect`。
- 需要人判断的：
  - 情形是否具体。「需要提高效率时使用」不合格；「准备把一个 skill 项目公开发布到 GitHub 时使用」合格。
  - 有没有概括流程。脚本只认得几个词，换了说法的流程概括要靠读。
  - 触发说法是不是用户真会说的话。
  - 与同一个用户可能装的其他 skill 是否容易混淆；容易混淆的，有没有写清不适用的情形。

脚本标为 `suspect` 的三类词都可能是误报。判为问题的标准：这个词所在的句子确实是在讲 skill 自己怎么做，或确实用了「我」「你」来指 AI 和用户。句子讲的是用户所处的情形时，不算问题。

### 简介的写法模板

```yaml
---
name: <小写字母-数字-连字符>
description: <具体情形一>、<具体情形二>或<具体情形三>时使用。触发说法：<斜杠命令>、<用户原话>、<英文原话>。<只处理什么；不适用于什么>。
---
```

### 简介的对照示例

不合格，概括了流程：

```yaml
description: 检查项目并给出清单，用户确认后补齐 README 和安装说明。
```

不合格，太空泛，没有情形：

```yaml
description: 帮助整理项目文档。
```

不合格，用了第一人称和第二人称：

```yaml
description: 我可以帮你检查 README 是否完整。
```

合格：

```yaml
description: 准备把一个 skill 项目公开发布到 GitHub、想知道它离公开发布还缺什么、或要复查已发布 skill 的安装说明和 README 时使用。触发说法：/github-ready、发布体检、publish readiness check。只用于含 SKILL.md 的项目，会修改该项目的文件；要推送或创建代码仓库时不适用。
```

## 第二部分 · 正文

正文是 AI 决定使用这个 skill 之后读的全部指示。读者是一个没有见过这个项目的 AI，它读完要能独立把事情做对。

### 推荐的结构

按下面的顺序组织。小标题的文字不强制，skill 用不到的块可以省略，脚本不检查小标题。

1. **概述**：这个 skill 是什么，核心原则是什么，一两句话。做的是一件有终点的事时，写明怎样算完成。
2. **何时使用**：适用的情形和不适用的情形，用列表。简介负责让 AI 决定读不读；这一节在读了之后帮 AI 确认用得对不对。不重复简介里的触发说法。
3. **核心做法**：流程型的 skill 写成带编号的步骤。每一步写明做什么、什么情况下停止。需要保证质量的流程带「检查、修正、再检查」的回路，并写明回路什么时候结束。
4. **速查**：用表格或列表列出执行时要反复查的东西，例如命令、取值的含义、对照关系。
5. **具体做法**：输出有固定样式的给出模板；各类情况分别怎么处理。
6. **常见错误**：容易做错的地方和避免的办法。

### 内容要求

- **只写 AI 原本不知道的内容。** 通用的常识、工具自带的用法不写。每一句都要问：去掉它，AI 会不会做错。
- **正文不超过 500 行。** 100 行以上的参考资料、可以反复使用的脚本和模板放进附带文件。
- **附带文件从正文直接引用，只引一层。** 正文里写明每个附带文件是什么、在哪一步读。附带文件不再指向更深一层的文件。超过 300 行的附带文件在开头放目录。
- **路径相对 skill 文件夹，用正斜杠。** 不写本机的绝对路径：skill 装到别的机器上，这类路径就失效了。
- **规矩讲理由。** 只有命令没有理由的规矩，AI 遇到没写到的情况时不知道怎么变通。
- **例子少而准。** 一个贴合实际的例子好于几个泛泛的例子。
- **术语前后一致。** 同一个东西只用一个叫法。
- **不写会过时的内容，不写这个 skill 是怎么开发出来的。**
- **不依赖某一个工具。** 只在某一个 AI 编程工具上才成立的内容不写进正文；判定办法见 `readme-standard.md` 末尾「可移植性」一段。
- **流程图只用于不容易看出来的判断点。** 线性的步骤用编号列表。

### 脚本能检查的

- 正文超过 500 行，标为 `suspect`。
- 正文引用了 skill 文件夹里的文件（如 `scripts/…`、`references/…`），而这个文件不存在，是必须修的问题。
- 正文里出现本机的绝对路径或反斜杠路径，标为 `suspect`。
- 超过 300 行的 Markdown 附带文件开头没有目录，标为 `suspect`。
- 只属于某一个工具的内容，标为 `suspect`（规则名以 `PORT-` 开头）。

### 需要人判断的

- 一个没有见过这个项目的 AI，只读正文和它指到的文件，能否把事情做对；哪里要靠猜。
- 流程有没有写清每一步的停止条件；该有回路的地方有没有回路。
- 规矩有没有讲理由。
- 正文有没有重复简介里的内容，或重复附带文件里的内容。
- 术语是否一致。
- 有没有写进开发经过、会过时的内容。

脚本标为 `suspect` 的路径可能是误报：正文在举例说明别人的项目路径、或展示命令输出时出现的路径不算问题；写给 AI 去读、去运行的路径才算。
