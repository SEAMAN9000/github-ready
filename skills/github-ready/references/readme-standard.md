# README 标准：八节逐节要求

体检和起草 README 都以本文件为准。每节分两类检查：「脚本能检查的」由 `scripts/checkup.py` 判定，「需要人判断的」由读原文判断。

## 全局规定

- **两份同构**：中文 `README.md` 与英文 `README.en.md` 都按本标准查，章节一一对应。
- **文件名**：中文是 `README.md`，英文是 `README.en.md`。
- **八节是下限**：缺一节就是必须修的问题；skill 自己加的节保留。额外的节建议放在「跑完之后」与「License」之间。
- **顺序**：按 1→8 排。顺序不对不算必须修的问题，报告里提一句建议。
- **不写开发过程**（需要人判断，全文适用）：读者能从文中看出作者用了什么内部流程、内部项目名或版本历史的，删掉。常见写法：「我们用 XX 流程开发了它」、内部讨论记录、路线图、内部目标文件的摘录。
- **不写防御性表述**（需要人判断，全文适用）：防御性表述指正在说明怎么做一件事时，突然转去罗列限制和可能出现的问题。它打断读者正在做的事，增加篇幅，对完成这件事没有帮助。这类内容属于开发记录，放在作者自己的开发文档里，不写进 README，也不放进随仓库发布的其他文件。常见写法：「本工具的局限」「已知问题」「注意：某些情况下可能……」「不保证……」。下面四样是本标准要求写的正常内容，不算防御性表述：第 2 节的不适合场景、第 6 节不会触发的说法、第 7 节不会改什么和失败时怎么办。它们各自写在规定的那一节里，不另外集中成一节或一个文件。
- **徽章**（需要人判断，全文适用）：README 顶部的状态小图标不要求。要加只加真实存在的（如 License 徽章），不加没有对应数据的装饰性徽章。
- **标题匹配**：每节有一个标准标题，脚本按它匹配，不计大小写，忽略 emoji 与标点。标题对不上但那一节看着像是写了的，标成 `suspect` 交人复查，不直接判成缺失。

## 第 1 节 · 标题 + 一句话

标准形态：H1 是 skill 的名字，紧跟一个引用块，一句话说清它做什么、用户得到什么。

- 内容要求：
  - H1 里包含 `SKILL.md` 头部的 `name`，完全一致或带修饰都可以（如「github-ready — 发布前体检与补齐」）。
  - 一句话里要有动作和产出物。「让开发更高效」这类口号不合格。
  - 标题下方放互链：`📖 English: [README.en.md](./README.en.md)`；英文版对应位置链回中文版。
  - 互链下方放一行快速安装：`npx skills add <owner>/<repo>`（可带 `-g`）。写法与第 5 节一致。
- 脚本能检查的：H1 存在；H1 包含 `name`；互链存在且指向的文件存在；快速安装行存在。
- 需要人判断的：这句话是否说清了做什么；快速安装命令与第 5 节是否一致。

## 第 2 节 · 什么时候用

标准标题：`## 什么时候用` / `## When to Use`。

- 内容要求：
  - 开头 2–4 句写典型场景或痛点，要具体。「每个 skill 想公开发布都得手工重做同样三件事」合格；「当你需要提升效率时」不合格。
  - ✅ 适合清单：2–4 条，每条是能对号入座的情形。
  - ❌ 不适合清单：2–4 条，尽量说明这类需求该去哪里。
- 脚本能检查的：节存在；✅ 和 ❌ 两个清单都在。
- 需要人判断的：场景是否具体，边界是否划清；两个清单是否各有 2–4 条。❌ 清单没说明该去哪里的，提一句建议。

## 第 3 节 · 用起来长什么样

标准标题：`## 用起来长什么样` / `## What It Looks Like`。案例写在这一节，不另做案例文件。

- 内容要求：
  - 一段对话记录，放在代码块里。每段话前面标明是谁说的（「用户：」「AI：」），演示前用一句话说明这个约定。目的是让没用过命令行的人一眼看懂。
  - 用户的第一句话是一句自然的话，并且用到「触发」一节里的一条说法，例如「给 my-skill 做一次发布体检」。不用斜杠命令开头，不带本机路径。斜杠命令只有一部分工具支持，写在「触发」一节里。
  - AI 的回复里，规则编号、内部代号、调试信息这类行删掉，只留用户读得懂、用得上的内容。
  - 覆盖完整过程：触发 → 需要用户确认的地方 → 结束时的产出。
  - 取自一次真实使用这个 skill 的记录，可以删减，不能编造。记录里的本机路径换成示例路径。只有一种改写是允许的：用户输入的是斜杠命令或带本机路径时，可以改写成意思相同的一句自然的话。AI 的回复只能删减，不能改写。内容会因项目而异的，在演示后说明哪些每次稳定、哪些会变。
  - 演示的是使用这个 skill，不是检查或修改这个仓库自己的过程。
  - 英文版的演示，原始输出不是英文的就放译文，并在演示前说明是译文。
  - 演示后用一句话总结用户要做的事（如「用户的操作：说一句话，阅读报告，回复一次」）。
- 脚本能检查的：节存在；至少有一个代码块。
- 需要人判断的：是不是对话的形式，有没有标明谁说的；用户的第一句话是不是自然的话、有没有用到触发说法；AI 的回复里有没有新手看不懂的规则编号一类内容；是否覆盖了需要用户确认的地方；有没有写开发过程；演示里的数字前后是否对得上；演示里的输出样子与这个 skill 现在的 `SKILL.md` 规定的是否一致；英文版放译文的有没有说明。

## 第 4 节 · Runtime 支持

标准标题：`## Runtime 支持` / `## Runtime Support`。

- 内容要求：
  - 三个工具各一小节：`### ✅ Claude Code`、`### ✅ Codex CLI`、`### ✅ OpenCode`。
  - 每个工具说清三件事：装到哪个路径、项目说明文件是哪个（`CLAUDE.md` 还是 `AGENTS.md`）、怎么触发。
  - 怎么触发：三个工具都会在用户的话与 `description` 相符时自动调用 skill，三个小节都写这一条。斜杠加名字（`/<name>`）的调用方式只写在 Claude Code 小节；另外两个工具的小节不写斜杠命令，除非作者在那个工具上试过。
  - 工具之间有差异的要交代（如 Codex CLI 没有 sub-agent，skill 用到时在那边怎么办）。
  - skill 会自动检测运行环境的，说明怎么检测、检测错了怎么手工指定。
- 脚本能检查的：三个工具的名字齐全；小节里写的安装路径在下表之内。
- 需要人判断的：三个小节是否都写全了上面三件事；差异说明是否准确，有没有漏掉该交代的替代做法。

**安装路径怎么判**：每个工具的小节里出现下表「可接受的路径」中任意一条即达标；写了表外的路径，或一条路径都没写，是必须修的问题。小节里已有表内的路径、另外又写了一条表外的工具目录路径时，脚本标为 `suspect`（规则名 `S45-ODDPATH`）：是笔误就是必须修的问题；是在说明别的事（例如提醒不要装到某个旧位置）就不算问题。

| 工具 | 可接受的路径 | 一键安装器装到哪（用户级 / 项目级） |
|---|---|---|
| Claude Code | `~/.claude/skills/`、`.claude/skills/` | `~/.claude/skills/` / `.claude/skills/` |
| Codex CLI | `~/.agents/skills/`、`.agents/skills/`、`~/.codex/skills/` | `~/.agents/skills/` / `.agents/skills/` |
| OpenCode | `~/.config/opencode/skills/`、`.opencode/skills/`、`~/.agents/skills/`、`.agents/skills/`、`~/.claude/skills/`、`.claude/skills/` | `~/.config/opencode/skills/` / `.agents/skills/` |

起草时，手动安装的路径写成与一键安装器相同的那条，两种装法装到同一个地方。`~/.codex/skills/` 是 Codex 的旧位置，Codex 仍然读它，所以已有的 README 写了它不算错，但新起草时不用它。发布仓库里的 `skills/<name>/` 是仓库的文件夹布局，不是安装位置，不能写成安装路径。

## 第 5 节 · 安装

标准标题：`## 安装` / `## Install`。

- 内容要求：
  - 第一小节是一键安装：`npx skills add <owner>/<repo>`。说明三件事：需要 Node.js；默认装到当前项目，`-g` 装到用户全局，`-a` 指定只装给某些工具；安装器会检测本机装了哪些 AI 编程工具并装到各自的位置。
  - 之后是手动安装，三个工具各一小节，命令放代码块，可以直接复制执行。Codex CLI 一节写明文件名必须保持 `SKILL.md`。
  - 每个工具末尾写一句怎么确认装上了。
  - 不写「贴一段提示词让 AI 自己装」这种装法。
- 脚本能检查的：一键安装命令含 `npx skills add`；三个工具的手动小节齐全；安装路径按第 4 节的表判；安装命令（`npx skills add`、`git clone`）里的仓库地址前后一致。正文里引用他人仓库的链接不算在内。
- 需要人判断的：命令能否照抄执行，有没有没写出来的前提；每个工具末尾有没有写怎么确认装上了，照着那句话做会不会因为缺前提而误以为没装上。

## 第 6 节 · 触发

标准标题：`## 触发` / `## Trigger`。

- 内容要求：
  - 一张中英对照的触发短语表，斜杠命令放第一行。
  - 写明哪些近似说法不会触发，以及想强制调用时怎么办。强制调用的办法只在某一个工具上成立的，写明是哪个工具。
- 脚本能检查的：节存在；表里的每条短语在 `SKILL.md` 的 `description` 里找得到。比对前会去掉空白、引号和并列分隔符（`/`、`、`、`,`），所以「排版 / 字体」与「排版」「字体」算一致。中英两列都算：英文列有内容，`description` 里就要有对应的英文说法。
- 需要人判断的：这些短语本身能否触发，覆盖够不够；强制调用的办法有没有写明适用的工具。

## 第 7 节 · 跑完之后

标准标题：`## 跑完之后` / `## After a Run`。

- 内容要求：
  - 流程：按序号讲会发生哪几步、哪一步要用户确认、大致耗时。
  - 产物：跑完后项目里多了什么文件，画文件树；三个工具的产物不同就各画一棵。
  - 改动范围：会改什么，不会改什么。
  - 失败时：中途失败停在哪、有没有半成品、怎么重来。
- 脚本能检查的：节存在。
- 需要人判断的：流程、产物、改动范围、失败时这四样是否都写了；文件树与实际产物是否对得上；失败时是否交代了停在哪、有没有半成品、怎么重来。

## 第 8 节 · License

标准标题：`## License`。

- 内容要求：一句话加指向 LICENSE 文件的链接。例：「MIT — 详见 [LICENSE](./LICENSE)」。
- 脚本能检查的：节存在；LICENSE 文件在仓库根；README 写的许可证名与 LICENSE 文件内容一致。
- 需要人判断的：无。

## 附：SKILL.md 的文件夹布局与可移植性

**文件夹布局**：一键安装器认得的布局是 `skills/<name>/SKILL.md`（推荐）、仓库根直接放 `SKILL.md`、`skills/<分类>/<name>/SKILL.md`、`.claude/skills/<name>/SKILL.md`。其他布局（如单数的 `skill/`）安装器找不到，是必须修的问题，改成推荐布局。

**可移植性**：脚本会扫描 `SKILL.md` 里只属于某一个工具的内容，一律标成 `suspect`（规则名以 `PORT-` 开头），由人复查：

- 某个工具独有的功能名（如 `TodoWrite`、sub-agent）。
- 某个工具专属的文件夹（如 `.claude/skills/`）。
- 只提 `CLAUDE.md`、没提 `AGENTS.md`。

判为问题的标准：换到另外两个工具上，这句话会让 skill 失效或指错地方。安装说明里出现各工具的路径是正常的；写明只服务某一个工具的 skill 使用该工具的功能名也是正常的。
